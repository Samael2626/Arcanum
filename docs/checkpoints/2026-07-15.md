# Checkpoint — ARCANUM — 2026-07-15

## Resumen

Sesión de revisión, corrección y despliegue enfocada en preparar ARCANUM para una futura publicación en Google Play. Se consolidó el lavado visual de Materia Arcana, se endureció la seguridad del backend y del grimorio, se añadieron pruebas de regresión y se desplegaron API y preview web móvil en producción.

## Cambios realizados

### Materia Arcana

- Se unificó el lenguaje visual de las nueve categorías visibles: hierbas, piedras, metales, inciensos, aceites, resinas, planetas, ángeles y signos.
- Las tarjetas y hojas de detalle comparten atmósfera planetaria, sellos, jerarquía tipográfica, animación de trazado y fallback visual seguro.
- Se creó `MateriaSpecimen` como capa visual común: intenta usar lámina histórica SVG para hierbas y cae en un grabado procedural semántico si el asset no existe o falla.
- Hierbas: 33 identidades; 27 láminas botánicas históricas SVG de dominio público y 6 siluetas procedurales propias.
- Piedras: 23 firmas individuales. Conservan una morfología mineral reconocible y añaden vetas, inclusiones o planos de exfoliación estables por slug.
- Metales: siete estados o formas alquímicas diferenciadas.
- Inciensos: 12 composiciones individuales según materia de origen, voluta y marcas de catálogo.
- Aceites: ocho recipientes rituales propios —oliva consagrada y siete correspondencias planetarias— en lugar de cuatro frascos repetidos.
- Resinas: cinco composiciones propias de exudación, lágrima o recipiente.
- Planetas, ángeles y signos mantienen 7, 7 y 12 sellos estables respectivamente.
- La identidad se deriva del slug normalizado y permanece igual entre VM, web y sesiones.

### Grimorio vivo y seguridad local

- Se renovaron lista, editor y detalle con estética de códice, atmósfera del regente, hora planetaria correcta y estados de carga/error que no confunden fallos de red con fallos criptográficos.
- Se corrigió el aislamiento entre sesiones: cambiar de usuario invalida la lista anterior y solicita nuevamente las entradas del usuario activo.
- Las escrituras nuevas usan un sobre versionado `v2:` con AES-256-GCM, nonce aleatorio de 96 bits y datos asociados `arcanum-grimoire:v2`.
- Las entradas antiguas AES-256-CBC siguen siendo legibles para evitar pérdida de contenido.
- Alterar el ciphertext GCM provoca fallo de autenticación en vez de entregar texto corrupto.
- La DEK continúa en `FlutterSecureStorage`, ligada al dispositivo.

> [!warning] Pendiente criptográfico
> Falta envolver la DEK con una KEK derivada del PIN mediante PBKDF2, integrar biometría/Android Keystore y bloquear el grimorio al enviar la app a segundo plano. El estado actual mejora integridad y compatibilidad, pero aún no completa el modelo final de recuperación y desbloqueo.

### Backend y secretos de producción

- Se retiraron de `app/core/config.py` los valores remotos incrustados y se dejaron defaults exclusivamente locales.
- `Settings` ahora distingue `development`, `test` y `production`.
- Producción rechaza iniciar con `SECRET_KEY` débil, `ADMIN_TOKEN` ausente/corto o `DATABASE_URL` local.
- Los endpoints admin responden 503 cuando administración está deshabilitada y comparan tokens con `secrets.compare_digest`.
- Railway recibió valores aleatorios nuevos para `SECRET_KEY` y `ADMIN_TOKEN`, además de `ENVIRONMENT=production`, sin mostrar sus valores en logs.
- El backend fue desplegado manualmente desde el working tree al servicio `Arcanum-Code`.
- Deployment Railway exitoso: `4d8f78f1-be6f-421e-9df7-a2a904eb17fa`.
- API pública verificada con HTTP 200: https://arcanum-code-production.up.railway.app

## Decisiones y notas

- Railway sigue siendo el backend canónico; Firebase Hosting solo sirve la preview web/PWA.
- La app de Play será Flutter Android nativa, no un simple enlace a Railway.
- Los grabados de materiales permanecen como vectores procedurales nativos del repo: escalan bien, animan por PathMetrics y no añaden peso de bitmap.
- Las láminas históricas continúan reservadas a las hierbas con procedencia y licencia documentadas en el manifest.
- Se prioriza compatibilidad: ninguna entrada CBC existente se migra destructivamente al guardar este cambio.
- No se imprimieron secretos de producción durante la configuración o verificación de Railway.
