# Checkpoint - Arcanum - 2026-06-27

## Resumen
Se recupero produccion de ARCANUM en Railway despues de una cadena de fallos en migraciones, startup y validacion de respuesta del endpoint Materia Arcana. El backend quedo desplegado y verificado en `https://arcanum-code-production.up.railway.app`.

## Cambios realizados
- `arcanum-api/migrations/versions/001_initial.py`: eliminado `checkfirst=True` invalido dentro de `op.create_table()`.
- `Dockerfile`: cambiado el arranque para usar `start-railway.sh`.
- `start-railway.sh`: agregado startup seguro para adoptar una base existente sin `alembic_version`; estampa `001`, `002` o `003` segun tablas/columnas presentes, corre `alembic upgrade head` y arranca Uvicorn en puerto `8000`.
- `arcanum-api/app/core/config.py`: agregadas banderas `RUN_STARTUP_MIGRATIONS` y `RUN_STARTUP_SEEDS`, ambas desactivadas por defecto.
- `arcanum-api/app/main.py`: migraciones y seeds de startup quedaron opt-in para evitar bloqueos durante el lifespan de FastAPI.
- `arcanum-api/app/schemas/materia_item.py`: ampliado `ItemType` para aceptar `resin`, `planet`, `sign` y `angel`, que ya existen en la data real.
- `arcanum-api/app/models/materia_item.py`: limpiado comentario obsoleto de tipos permitidos.

## Decisiones y notas
- La base Supabase ya tenia tablas pero no tenia `alembic_version`; intentar correr `001` desde cero producia `DuplicateTable: relation "users" already exists`.
- La estrategia elegida fue adoptar la BD existente con `alembic stamp` segun el estado real, no borrar tablas ni resetear datos.
- Railway tiene el dominio apuntando a `targetPort: 8000`; por eso Uvicorn quedo fijado explicitamente a `8000` en `start-railway.sh`.
- Se separo la responsabilidad: Docker/startup script maneja migraciones; FastAPI lifespan no bloquea arranque por migraciones o seeds salvo opt-in via env.
